# 00. 용어집과 읽는 법

> 이 문서는 01~10번 해설 문서를 읽기 전에 한 번 보는 공용 안내서다. 세 사람이 같은 말을 같은 뜻으로 쓰게 하는 것이 목적이다.

## 2. 문서 한 개의 구조 (모두 같다)

1. 한 줄 역할
2. 흐름 표 (입력 → 처리 → 출력)
3. 절별 해설 (코드 조각 + 쉬운 말)
4. 핵심 가정 3개
5. 코드 검토 결과 (지적, 판정, 근거)
6. 다른 문서와의 연결, 제안서에 쓰인 숫자
7. 본선 예상 질문 3개와 답
8. 스스로 확인 문제 3개 (답은 부록)
9. 5분 설명 대본 (직접 채우기)
10. 세 문장 요약 (직접 채우기)

공부 순서 권장: 1 → 2 → 4 → 3 → 6 → 7 → 8 → 5. 5절(코드 검토)은 코드가 익숙해진 뒤에 읽어야 뜻이 통한다. 9절과 10절은 다 읽은 뒤 직접 채운다.

## 3. 5절 판정의 뜻

| 판정 | 뜻 | 할 일 |
|---|---|---|
| 진짜 버그 | 지적이 맞고 결과 숫자나 그림이 틀어진다 | 고치고, 영향받는 제안서 숫자를 다시 확인 |
| 문제 없음(오해) | 코드는 의도대로 동작한다. 지적한 쪽이 오해했다 | 왜 오해가 생겼는지 읽어 두면 질의응답에 도움 |
| 개선 제안 | 결과에는 영향이 없지만 더 안전하거나 읽기 쉬운 쓰기 방법이 있다 | 시간 남을 때 |

각 지적에는 `checks/checkNN.m`에 확인용 코드가 있다. PASS는 "코드가 의도대로 동작함(지적이 오해)", FAIL은 "지적이 맞음"이다. 결과는 `checks/check_results.txt`에 모아 두었다.

| 천저(nadir) | 위성 바로 아래. 기울기 0° | 방식 "천저 고정" |

| 기동 속도 | 1초에 몇 도 기울일 수 있나. 1.5°/s | `P.slewRate` |

| 관측 표본 | 1.5초마다 한 번. 풋프린트(빔이 지면에 닿는 원) 하나를 지나는 시간 | `P.profDt = 1.5` |
| 강수 기록(profile) | 관측 표본 하나에서 얻는 높이별 비 세기. 성공 기준의 "개수"는 이것을 센 것 | `evaluate` |

## 6. 용어 (큐와 계획)

| 용어 | 뜻 | 코드에서 |
|---|---|---|
| 큐(cue) | "지금 어디에 비가 있다"는 거친 정보. 실제 운용은 천리안 2A + KIM, 모의에서는 IMERG Early(또는 Final에 가짜 오차) | `cueScene` |
| 큐 지연 | 큐 장면이 정해진 뒤 위성이 관측하기까지 걸린 시간. 기준 15분 | `P.cueL = 15` |
| 가짜 오차 | Final을 큐로 쓸 때 현실성을 주기 위해 섞는 오차. 호우 핵을 알아볼 확률 0.72, 위치 오차 3 km, 속도 오차 | `P.pDet`, `P.posSd`, `P.velSd` |
| 나우캐스트 | 큐 장면을 이동 벡터로 밀어서 "관측 시각에 비가 어디 있을까"를 예측한 장면 | `cueScene` |
| 보정표 | 큐 강도 구간별로 "실제로 호우일 확률"을 2023년에서 세어 둔 표. 30분 뒤(lag 1)와 60분 뒤(lag 2) | `calibrate`, `P.edges`, `P.lags` |
| 보상 격자 | 통과 중 각 시각 × 각 기울기에 "여기를 보면 호우일 확률"을 적은 표 | `rewardGrid` |
| DP(동적계획법) | 보상 격자 위에서 기동 한계를 지키며 보상 합이 가장 큰 기울기 경로를 찾는 방법 | `dpPlan` |
| 기존 방식(greedy) | 큐 강도 10 mm/h 이상인 점을 표적으로 정해 순서대로 겨냥하고 3초씩 응시하는 처음 설계 | `greedyPlan`, `P.dwell`, `P.greedyThr` |
| 위치고정 | 큐 장면을 밀지 않고 그 자리에 있다고 보는 DP | 방식 "DP 위치고정" |
| 완벽 정보(상한) | 정답(Final)을 큐로 쓰고 오차도 없다고 가정. 이보다 좋아질 수는 없다는 천장 | 방식 "DP 완벽 정보" |
| 이득(gain) | 어떤 방식의 호우 기록 수 ÷ 천저 고정의 호우 기록 수 | `methods.csv`의 `gainHeavy` |

## 7. 용어 (통계)

| 용어 | 뜻 |
|---|---|
| 학습 / 검증 | 보정표는 2023년으로 만들고(학습), 2024·2025년에 적용해 성적을 낸다(검증). 같은 해로 둘 다 하면 성적이 부풀려진다 |
| 부트스트랩 | 하루(또는 5일 묶음)를 무작위로 다시 뽑아 수백 번 계산해 "결과가 얼마나 흔들리나"를 보는 방법 |

| 5일 블록 | 날씨는 며칠씩 이어지므로 하루가 아니라 5일 묶음으로 뽑아 흔들림을 덜 작게 본 것 |
| 시드 | 난수의 시작값. 연도별로 고정해 다시 돌려도 같은 숫자가 나오게 한다 |
| 미래 정보 누수 | 큐가 관측 시각 뒤의 장면을 보는 실수. 성적이 거짓으로 좋아진다. 코드는 "마지막으로 완료된 30분 슬롯"만 쓴다 |

## 9. 결과 파일 읽는 법

- `out/dp_step*/summary.txt`: 사람이 읽는 요약. 먼저 본다.
- `out/dp_step*/methods.csv`, `cases.csv`: 방식(또는 경우)별·연도별 숫자 표. 제안서 숫자의 출처.
- `out/dp_step*/key_*.json`: 같은 숫자를 프로그램이 읽기 쉽게 둔 것.
- `out/dp_step*/results.mat`: MATLAB 전체 결과. 다시 그림을 그릴 때.
- `out/run_log.csv`, `matlab/out/run_log.csv`: 언제 무엇을 돌려 어떤 숫자가 나왔는지 한 줄씩 쌓인 기록.
- 제안서 숫자는 전부 이 파일들에서 스크립트(proposal/update_v3_dp*.py)로 읽어 넣었다. 손으로 친 숫자는 없다.

## 10. 세 사람이 서로 설명하는 날 진행 제안

1. 각자 담당 문서의 9절(5분 대본)로 설명. A → B → C 순서(의존 관계 순).
2. 설명 뒤 다른 두 사람이 그 문서의 8절(확인 문제)을 풀어 보고 답을 맞춘다.
3. 각 문서 7절(예상 질문)을 서로 물어보며 답을 다듬는다. 답은 3문장 이내로.
4. 5절에서 '진짜 버그'로 판정된 것이 있으면 어떻게 고쳤고 제안서 숫자가 바뀌었는지 함께 확인한다.
